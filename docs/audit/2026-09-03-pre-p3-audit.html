Verdict: safe to start P3 — with one condition

Nothing blocks P3 from beginning. The build is green, all 104 tests pass, and cross-tenant isolation was re-verified today against a live PostgreSQL 16 instance: all 17 business tables refuse cross-tenant read, insert, update, tenant-move and delete, and the stock_movements append-only trigger rejects even owner-level writes.

The condition is that F1 and F5 are P3's own work, not follow-ups. Both are live weaknesses in the membership layer P3 is about to rewrite, and one of them (F1) is currently held shut only by a primary key that the P3 plan explicitly removes. Ship P3 without addressing them and the phase makes the system less safe, not more.

Separately, F2 and F3 must be settled before the sync engine and before any pharmacy runs on more than one device. Neither affects P3.

Nothing found here is exploitable today: the SQL has never been applied to a live Supabase project, and there is no authentication yet.

Section 2

Findings in detail

F1

Any authenticated user can claim any pharmacy as its owner

Critical P3 scope

The insert policy on profiles validates who you are but never which tenant you attach yourself to:

create policy profile_insert on profiles
  for insert with check (user_id = auth.uid());   -- pharmacy_id unchecked

Today a second claim is blocked, but only by accident: profiles.user_id is the primary key, so an existing member cannot insert a second row. A user with no profile row has nothing to collide with. Verified live against the committed schema:

Evidence — user C exists in auth, belongs to nothing

set role authenticated; set app.uid = '3333…3333';
insert into profiles (user_id, pharmacy_id, role)
values ('3333…3333', 'bbbb…00b1', 'owner');
INSERT 0 1

auth_pharmacy_id = bbbbbbbb-0000-0000-0000-0000000000b1
sales visible:     1
customers visible: 1
is_owner =         true

The attacker needs a pharmacy id, which is not secret: it is generated on the device, stored in localStorage.fp_pharmacy_id, and stamped onto every row that will ever sync. pharmacy_insert lets anyone create a pharmacy, so a normal signup supplies the account to attack from.

Why this matters most for P3. The plan replaces profiles(user_id PK) with memberships(user_id + pharmacy_id PK). That removes the only thing currently holding this shut, and turns a one-shot accident into a repeatable one. docs/P3-PLAN.md covers validating the active pharmacy in auth_pharmacy_id() (line 137) but says nothing about the insert policy. It needs to.

F2

Backup and restore silently drop the entire stock ledger

High

ALL_TABLES in src/lib/db/local.ts:351 lists 16 tables and omits stock_movements. Both exportAll() and importAll() iterate that list and nothing else.

  • Restore onto a fresh device (the phone-was-lost case): the ledger comes back empty. Every movement ever recorded is gone.
  • Restore onto a device that already has movements: importAll() never clears stock_movements, so the old device's movements survive next to wholesale-replaced business rows, referencing batch and sale ids that no longer exist.

Displayed stock survives, because qty_in_stock is in the backup and screens read the cache — P2b happens to protect this case — and planCacheRebuild()'s no-history guard stops the empty log from zeroing anything. But the log the architecture calls the source of truth is destroyed by the feature the app actively nags the user to run every seven days.

This compounds R3. The backfill runs only inside the Dexie v4 upgrade, which fires once per device, so a restored device can never rebuild what it lost. The settings screen's !hasMovements branch tells the user "অ্যাপটি একবার বন্ধ করে আবার খুলুন" — close and reopen the app — which cannot work, because the upgrade will not run again.

Note for whoever fixes it: adding the table to ALL_TABLES is not sufficient on its own, because importAll() calls table.clear() and the append-only guard registers a deleting hook that throws. The restore path needs a deliberate answer, not a one-line list edit.

F3

Every backfilled movement will be rejected by the server

High

backfillId() in src/lib/stock/reconstruct.ts:77 returns mv-<refType>-<refId>, and that string is used as the movement's id at lines 103 and 159. The server column added in P2b is id uuid primary key.

Evidence — against the committed schema

insert into stock_movements (id, …) values ('mv-sale_item-abc', …);
ERROR:  invalid input syntax for type uuid: "mv-sale_item-abc"

Only movements created after the upgrade are affected — those go through buildMovement(), which calls uuid(). Everything the P2 migration generated, which is the whole of each device's pre-migration history, would fail on first push.

Same class of problem, one line away: medicine_id: medicineOf.get(batchId) ?? '' (reconstruct.ts:105) can emit an empty string into a uuid not null column.

F4

markSynced() cannot clear dirty on a movement

Medium Already documented

Confirmed in code. attachSyncHooks() (local.ts:188) registers an updating hook on every table in SYNCED_TABLES, which includes stock_movements; attachAppendOnlyGuard() (local.ts:164) then registers a second updating hook on the same table that throws unconditionally. markSynced() (sync/state.ts:86) is a plain table.update(id, { dirty: 0, … }), so push would mark a movement sent and immediately throw.

The handoff records this. Listed here so the register is complete.

F5

Invite codes are readable across every tenant

Medium P3 scope

invite_lookup grants select on any invite that is unused and unexpired, with no tenant predicate — deliberately, so a code can be checked before you belong anywhere. The effect is that every authenticated user can enumerate every live invitation in the system.

Evidence — user A, a member of pharmacy A only

select pharmacy_id, code, role from invites;
aaaa…00a1 | code-aaaa | staff
bbbb…00b1 | code-bbbb | staff   <- another pharmacy's live code

If joining a pharmacy is done by presenting a code, this is a cross-tenant join path, not merely an information leak. P3 owns invites and membership, so it is the right phase to close it — for example by looking codes up through a security definer function that returns only a yes-or-no, rather than by a readable policy.

F6

Soft-delete filtering is inconsistent, and the docs say it isn't

Medium

The handoff states: "Every read filters deleted rows out (isLive, liveArray)." Many reads filter on status === 'completed' and never look at deleted_at — data.ts lines 201–203, 619, 718–721, 793–799 and 835–843, covering the dashboard, the daily report, the monthly report and the cash summary.

Harmless today, because the six tables that are ever soft-deleted are customers, customer ledger, expense categories, batches, medicines and cash sessions; sales, expenses and due payments are cancelled rather than deleted. It stops being harmless the moment the sync engine applies a deleted_at tombstone from another device, at which point deleted rows start counting toward today's takings.

F7

deleteBatch() moves visible stock without a movement

Low

data.ts:1420 refuses to delete a batch that has stock entries, sale items, adjustments or return items. A batch carrying only a backfilled opening_balance movement passes all four guards. It is then soft-deleted, vanishes from every screen, and its movement stays live and orphaned.

Not a correctness bug — verifyStockIntegrity() and planCacheRebuild() both filter to live batches, so nothing mismatches. But it is a tenth stock-affecting path, its transaction does not include stock_movements, and the ledger no longer explains a change the user can see. A write_off movement would be the honest record.

F8

Dead code, and nothing in the toolchain to catch more of it

Low

STOCK_SOURCE is fully gone from code — zero references across .ts, .tsx and .sql. It survives only in two prose mentions in the handoff, one of which is wrong (see M2).

  • computeBatchQty() and computeAllBatchQty() — movements.ts:70, 76. Zero call sites since P2b removed the last one. Exported, documented, unreachable.
  • recomputeStockCache() — no caller. Expected, since the sync engine does not exist, but it means the repair path in the P2b design is unreachable from the running app.
  • formatTaka — unused import, dashboard/page.tsx:8.
  • Unused generic <T> on markDeleted, data.ts:40.
  • public/brand/*.svg — four files, roughly 53 kB shipped in the export, referenced by nothing. BrandMark.tsx inlines its own SVG.

None of these are caught by the toolchain: tsconfig.json sets strict but not noUnusedLocals, and there is no ESLint configuration, so next build skips linting entirely and next lint drops into interactive setup. There is no lint gate at all.

The structural cause is one line: vitest.config.ts sets environment: 'node' with no IndexedDB shim. Every function that touches Dexie is therefore untestable as the project stands, and all 104 passing tests cover pure logic only.

Verified by hand in a past session, never codified

  • P1 echo loop. A simulated pull of ten server rows selecting zero rows for push. Proved in a browser; no test.
  • P2 invariants I1–I8. Run against a seeded database with a cancelled sale, cancelled stock entry, cancelled adjustment and two returns. No fixture in the repo reproduces it.
  • P2b drift check. Add stock, sell, confirm cache equals log. Browser only.
  • P2b cache repair. recomputeStockCache() restoring a drifted counter from 999 to 40, leaving dirty: 0, idempotent on a second run. Exercised through a temporary window hook that was correctly removed before committing — and with it, the only evidence.
  • Every RLS run, including this one. Valuable, repeatable, and not in the repository. A committed .sql harness would make it a command rather than a memory.

What is genuinely solid

  • The cross-check pair earns its keep. independentReplay and reconstructMovements really are written differently, and the tests exercise the disagreement path, not just agreement — stock-reconstruct.test.ts:290 feeds a deliberately broken replay and asserts the check fails, and :298 drops a sale and asserts the same. That is the difference between a guard and a decoration.
  • Fixtures are realistic. Cancelled sales, cancelled entries, cancelled adjustments, multiple returns on one sale and soft-deleted rows are all covered.
  • No tests reference removed functionality. Nothing mentions STOCK_SOURCE.
  • Weak assertions are rare: two found — toBeDefined() at stock-reconstruct.test.ts:146 and toBeTruthy() at business-rules.test.ts:44 — and both sit beside stronger assertions on the same value.

Section 7

Also worth knowing

  • The window to fix F1 and F5 for free is still open. The SQL has never been applied to a live Supabase project. Editing files no database has consumed costs nothing; the same change after launch is a migration against live accounts.
  • pharmacy_insert lets any authenticated user create a pharmacy — with check (auth.uid() is not null). Correct for signup on its own. Combined with F1 it supplies the legitimate account an attacker operates from.
  • The v4 checkpoint is correct. It snapshots SYNCED_TABLES_V3, 14 tables, deliberately excluding stock_movements — which is empty before the upgrade that creates it. No gap here.
  • Two hooks, one table, right order. attachSyncHooks runs before attachAppendOnlyGuard, so a movement is stamped and then refused. The net behaviour is correct; it is only markSynced (F4) that needs the guard to make an exception it currently cannot.
  • No TODO, FIXME, HACK or deprecation markers anywhere in src/, and no leftover feature flags beyond the ones listed in F8. For a codebase four phases into a rewrite, that is unusually tidy.
  • The service worker shell list is stale but harmless — public/sw.js caches /, /dashboard/, /sales/, /add-stock/ and the manifest, under a cache key still named asshifa-shell-v2. Everything else is cached on demand.
